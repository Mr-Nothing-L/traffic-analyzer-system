# 三层审查架构:专家 → 裁决 → 锚定核验

## 背景

系统对每个视频的分析流水线采用三层递进审查,每层有不可混淆的职责边界。

## 决策

采用三层审查架构:

1. **事件专家层(事实识别)** — N 位事件专家并行运行,每人只负责一个事件类别的"看到/没看到"。只报事实,不做任何排除或冲突判断。产出事件候选。

2. **裁决层(冲突解决)** — 单次 VLM 调用,接收全部事件候选,根据业务规则(如"应急车道静止→双事件"、"事故场景中静止车辆不重复判定为违停")裁决哪些候选保留、哪些排除。产出事件结果。

3. **锚定核验层(幻觉修正)** — 可选。对裁决阳性结果用原始粗关键帧再做一次 VLM 调用,验证关键视觉元素能否在画面中锚定。无法锚定的阳性判定被视为幻觉并推翻。

## 原因

三层分离使每层 VLM 调用的任务单一化,提高准确率:
- 专家层关注单事件的视觉事实,prompt 简短聚焦。
- 裁决层关注跨事件语义,可以用全部候选做全局判断。
- 锚定核验层专门对抗幻觉,用不同帧集(原始粗帧)交叉验证。

若合并为单步(一次 VLM 调用同时识别 + 裁决 + 验证),prompt 过长、职责过载,准确率下降。

## 影响

- 分析延迟 = 三次串行 VLM 调用(专家并行算一轮 + 裁决一轮 + 核验一轮),但准确性优先于速度。
- 锚定核验可独立开关(`grounding_check_enable`),不影响其他两层。
- **裁决 VLM 输出不保证完整性**:裁决 JSON 可能遗漏某些 event_id。代码层面有补偿机制——缺失事件触发重试(最多 5 次),仍遗漏则重跑对应专家,最终仍失败则用原始候选降级回填(`fallback_candidates_to_event_results`)。
